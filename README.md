# cpp_hse_ripoff

Домашние работы по C++. Каждая работа — отдельный каталог `NN/` со своим
Makefile, сборка через Make, тесты на GoogleTest (из apt), стиль — Google C++
Style.

[![CI](https://github.com/Unknown-reader/cpp_hse_ripoff/actions/workflows/ci.yml/badge.svg)](https://github.com/Unknown-reader/cpp_hse_ripoff/actions/workflows/ci.yml)

## Требования

- Компилятор `g++` с поддержкой C++20 (в CI дополнительно проверяется `clang++`)
- `make`
- `libgtest-dev` — заголовки и статические библиотеки GoogleTest (нужен для
  `make build`, `make test`, `make sanitize`, `make coverage`)
- `clang-format`, `clang-tidy`, `cppcheck`, `cpplint` — инструменты качества
  (нужны только для `make lint`, `make format` и `make format-check`)
- `gcovr` — для `make coverage`

Все зависимости есть в штатных репозиториях Ubuntu/WSL (`cpplint` и `gcovr` — в
`universe`), Python/pip не нужен. Установка на «чистой» системе:

```bash
sudo apt-get install -y make g++ libgtest-dev \
  clang-format clang-tidy cppcheck cpplint gcovr
```

## GoogleTest

Все работы используют GoogleTest и берут его из системных пакетов
(`libgtest-dev`), без копирования библиотек в репозиторий. GoogleTest
подключается только при линковке тестового бинарника (`GTEST_LDLIBS` в
`NN/Makefile`):

```make
GTEST_LDLIBS = -lgtest -lgtest_main -pthread
```

GoogleTest обязателен для `make build`, `make test`, `make sanitize` и
`make coverage` — без него не соберется тестовый бинарник (`<gtest/gtest.h>` и
библиотеки). Для `make lint` и `make format` gtest не нужен.

Пример тестов на GoogleTest — `01/tests/test_solution.cpp`.

## Быстрый старт

```bash
make help                 # список команд
make test  HW=01          # собрать и прогнать тесты работы 01
make build HW=01          # собрать работу, не запуская тесты
```

Собрать и протестировать сразу все работы из `HWS`:

```bash
make build
make test
```

## Команды

| Команда | Назначение |
|---|---|
| `make build [HW=NN]` | Собрать все или только работу `NN` |
| `make test [HW=NN]` | Собрать и прогнать тесты |
| `make sanitize [HW=NN]` | Сборка и тесты под ASan/UBSan |
| `make coverage [HW=NN]` | Отчет о покрытии (`coverage/index.html`) |
| `make lint [HW=NN]` | cpplint + clang-tidy + cppcheck |
| `make format` | Автоформатирование clang-format по всему репозиторию |
| `make format-check` | Проверка форматирования (как в CI) |
| `make clean` | Удалить каталоги сборки и отчеты покрытия |

Результаты сборки складываются в `build/NN/`, санитайзеры — в
`build-asan/NN/`, покрытие — в `build-cov/NN/` (все каталоги в `.gitignore`).
Отчет покрытия отдельной работы пишется в `NN/coverage/`, сводный отчет по всем
работам — в корневой `coverage/`.

Команды можно вызывать и напрямую из каталога работы:

```bash
cd 01
make test
```

## Как добавить работу

1. Создайте каталог `NN/` (например, `02/`).
2. Скопируйте `Makefile` из любой готовой работы (он самодостаточен, менять в
   нем ничего не нужно):
   ```bash
   mkdir -p 02 && cp 01/Makefile 02/
   mkdir -p 02/include/hw02 02/src 02/tests
   ```
3. Добавьте заголовок, исходник и тест по образцу `01/`.
4. **Допишите номер в `HWS`** в корневом `Makefile` (например, `HWS := 01 02`),
   чтобы корневые команды видели работу.
5. Проверьте локально: `make test HW=02`, `make lint HW=02`,
   `make sanitize HW=02`.

## Стиль кода

Проект следует [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html):

- отступ 2 пробела, ширина 80 колонок (`.clang-format`, профиль `Google`);
- имена: `CamelCase` для типов и функций, `snake_case` для переменных,
  `snake_case_` для приватных полей, `kCamelCase` для констант;
- `#define`-guard'ы в заголовках (`HW07_SOLUTION_HPP_`);
- порядок `#include` проверяет cpplint.

Проверки выполняют три инструмента: `clang-format` (форматирование),
`cpplint` (правила Google) и `clang-tidy` + `cppcheck` (статический анализ).
Все они блокирующие — CI упадет при нарушении.

## CI/CD

Пайплайн описан в `.github/workflows/` и запускается автоматически.

**`.github/workflows/ci.yml`** — на каждый `push` и `pull_request` в `main`,

**`.github/workflows/pages.yml`** — по push в `main`: HTML-отчет о покрытии
публикуется на GitHub Pages.

- **Settings → Pages → Source = GitHub Actions** — иначе `pages.yml` не
  задеплоит отчет.
- (Необязательно) **Settings → Branches** — защита `main` с обязательными
  зелеными проверками CI.

## Мини-гайд: как работают Makefile этого репозитория

Этот раздел временный — объясняет устройство `Makefile` (корневого и в каждой
работе) с нуля, чтобы читать код было не страшно.

### 1. Идея make

`make` — это утилита, которая умеет собирать проект по правилам. Правила
хранятся в файле с именем `Makefile`. При запуске `make <что-то>` `make`
читает файл, находит правило для `<что-то>` и выполняет его команды.

Фундаментальная форма правила:

```make
цель: зависимости
	команды
```

- **цель** — что мы хотим получить (файл `build/01/hw01_tests` или условное
  имя вроде `test`, `clean`);
- **зависимости** — от чего зависит цель (файлы или другие цели);
- **команды (рецепт)** — шелл-команды, которые надо выполнить.

Знаменитая особенность: если у цели есть зависимости-файлы, `make` сравнивает
временные метки. Если файл цели **новее** всех своих зависимостей — `make`
пишет «Nothing to be done» и ничего не делает. Именно поэтому повторный
`make build` не компилирует заново: `make` считает, что все уже актуально.

`make` — **не язык программирования**, а декларативное описание зависимостей.
Поэтому в Makefile не бывает «программы с началом и концом», там просто набор
правил.

### 2. Правила из нашего кода

Возьмем правило сборки тестового бинарника из `01/Makefile`:

```make
$(TEST_BIN): $(TEST_OBJS) $(LIB)
	@mkdir -p $(dir $@)
	$(CXX) $(CXXFLAGS) $(LDFLAGS) -o $@ $(TEST_OBJS) $(LIB) $(GTEST_LDLIBS)
```

Сначала подставляются переменные — `$(TEST_BIN)` — и правило превращается во
что-то вроде `build/01/hw01_tests: build/01/tests/test_solution.o build/01/libhw01.a`.
Дальше:

- строка с командой **обязательно начинается с таба** (символ табуляции,
  пробелы не подходят — типичная ошибка новичков);
- рецепт выполняется в шелле (bash), каждая строка — отдельный вызов;
- если хоть одна команда вернет ненулевой код возврата — `make` останавливается
  с ошибкой.

### 3. Специальные символы в начале команд

| Символ | Смысл | Пример у нас |
|---|---|---|
| `@` | не печатать команду перед выполнением | `@mkdir -p ...`, `@echo ...` |
| `-` | не останавливаться, если команда упала | `-include ...` (см. ниже) |
| `\` (в конце строки) | перенос команды на следующую строку | флаги компилятора, длинные `gcovr` |

Пример переноса из `01/Makefile`:

```make
CXXFLAGS ?= -std=c++20 -Wall -Wextra -Wpedantic -Wshadow \
	-Wconversion -Wsign-conversion -g
```

### 4. Переменные

Переменные задают так:

| Оператор | Поведение | Пример |
|---|---|---|
| `:=` | значение вычисляется **сразу** | `NAME := $(notdir $(CURDIR))` |
| `=` | значение вычисляется **в момент использования** (лениво) | (в проекте не используется) |
| `?=` | задать, **если еще не задана** | `CXX ?= g++`, `CXXFLAGS ?= ...` |
| `+=` | **добавить** к текущему значению | `CPPFLAGS += -Iinclude`, `CXXFLAGS += -Werror` |

Подставляются так: `$(ИМЯ)`.

Важная деталь про `?=`: `make` автоматически превращает **переменные
окружения** в переменные make. Поэтому:

```bash
WERROR=1 make build      # в make WERROR уже равна 1 → добавится -Werror
```

Работает блок:

```make
ifeq ($(WERROR),1)
  CXXFLAGS += -Werror
endif
```

Приоритет переопределения: **командная строка > окружение > файл**. Поэтому
`?=` — безопасная форма: локально переменная берется из файла, а при желании ее
можно перезаписать `make build CXXFLAGS="..."`.

Встроенные переменные, которые мы переиспользуем:

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `CXX` | `g++` | компилятор C++ |
| `CPPFLAGS` | пусто | препроцессорные флаги (здесь `-Iinclude`) |
| `CXXFLAGS` | свои | флаги компиляции |
| `LDFLAGS` | пусто | флаги компоновки (здесь — `--coverage`, санитайзеры) |
| `AR` | `ar` | архиватор |
| `SHELL` | `/bin/sh` | шелл, в котором идут рецепты (в корне задан `/bin/bash`) |

### 5. Автоматические переменные

Внутри рецепта `make` подставляет специальные переменные:

| Переменная | Значение |
|---|---|
| `$@` | имя цели |
| `$^` | **все** зависимости |
| `$<` | **первая** зависимость |
| `$*` | часть имени, совпавшая с `%` в шаблоне |

Примеры из `01/Makefile`:

```make
$(LIB): $(LIB_OBJS)
	@mkdir -p $(dir $@)     # $(dir $@) — каталог цели (функция dir)
	ar rcs $@ $^            # архив из всех объектов
```

и построчное правило компиляции:

```make
$(BUILD_DIR)/%.o: %.cpp
	@mkdir -p $(dir $@)
	$(CXX) $(CPPFLAGS) $(CXXFLAGS) -MMD -MP -c $(abspath $<) -o $@
```

`$(abspath $<)` — функция, превращающая относительный путь исходника в
абсолютный — так Make более устойчив к каталогам, из которых запущен.

### 6. Функции GNU make

Функции выглядят как `$(имя аргумент1,аргумент2)`.

| Функция | Что делает | Пример у нас |
|---|---|---|
| `$(wildcard ШАБЛОН)` | список существующих файлов | `LIB_SRCS := $(wildcard src/*.cpp)` |
| `$(patsubst ШАБЛОН,ЗАМЕНА,СПИСОК)` | переписать каждый элемент | `src/%.cpp` → `$(BUILD_DIR)/src/%.o` |
| `$(notdir ПУТЬ)` | убрать каталоги из пути | `NAME := $(notdir $(CURDIR))` → `01` |
| `$(abspath ПУТЬ)` | абсолютный путь | `ROOT := $(abspath ..)` |
| `$(dir ПУТЬ)` | каталог пути | `mkdir -p $(dir $@)` |
| `$(if УСЛ,ТО,ИНАЧЕ)` | выбрать одну часть | см. ниже |
| `$(words СПИСОК)` | количество элементов | `Отформатировано файлов` |
| `$(shell КОМАНДА)` | выполнить шелл-команду | список `FORMAT_SOURCES` |

`$(if ...)` из `01/Makefile`:

```make
ALL_TARGETS := $(LIB) $(if $(TEST_SRCS),$(TEST_BIN))
```

Если `$(TEST_SRCS)` не пуст (тесты есть) — к сборке добавляется тестовый
бинарник; если тестов нет — собирается только библиотека.

**Самое главное:** `%` в `patsubst` и в правилах — это не шелл-звездочка, это
шаблон «любая строка». А `*` в `$(wildcard src/*.cpp)` — это уже настоящий
глоб шелла/файловой системы.

### 7. Спеццели `.PHONY` и `.DEFAULT_GOAL`

Цели вида `clean`, `test`, `lint` не создают одноименных файлов. Чтобы `make`
не думал, будто файл `clean` уже существует, их перечисляют в `.PHONY`:

```make
.PHONY: build test sanitize coverage clean lint help
```

`.DEFAULT_GOAL` задает цель по умолчанию (что случится при голом `make`):

```make
.DEFAULT_GOAL := build     # в 01: голый make соберет работу
.DEFAULT_GOAL := help      # в корне: голый make покажет справку
```

### 8. Раскрытие секрета `-include` и `%.o: %.cpp`

В `01/Makefile` есть два «магических» места.

**Паттерн-правило**:

```make
$(BUILD_DIR)/%.o: %.cpp
```

Одно правило обслуживает ВСЕ пары исходник→объект одновременно: где бы ни лежал
`src/solution.cpp`, объект `build/01/src/solution.o` собирается по этой формуле.
`%` ловит середину пути. Именно поэтому объектные пути заранее вычисляются через
`patsubst` для каждого исходника.

**Автозависимости**:

```make
- $(CXX) ... -MMD -MP -c ... -o $@     # при компиляции пишется .d рядом с .o
- include $(LIB_OBJS:.o=.d) $(TEST_OBJS:.o=.d)
```

Флаги `-MMD -MP` заставляют компилятор дополнительно выписать в файлы `.d`
зависимости от заголовков (`#include "solution.hpp"`). Строка
`-include ... .d` в конце подключает эти списки: если поменяли заголовок —
`make` узнает об этом из `.d` и пересоберет нужные объекты. Минус перед
`include` означает «не ругаться, если файла еще нет» (первая сборка).

### 9. Рекурсивный make

Когда проект состоит из нескольких подпроектов, Makefile вызывает сам себя для
подкаталогов. Тут важны `$(MAKE)` (не голое `make`) и `-C`:

```make
build test sanitize:
	@for d in $(DIRS); do \
		$(MAKE) --no-print-directory -C $$d $@ || exit 1; \
	done
```

- `-C dir` — выполнить `make` в каталоге `dir`;
- `$@` там, где команды, — имя текущей цели (`build`, `test` или `sanitize`);
  получается «пробросить» цель вниз;
- `$$d` — двойной доллар: `make` видит `$d` как данные и не мешает шеллу
  раскрыть переменную цикла `d`;
- `|| exit 1` — если дочерний `make` упал, остановиться.

Так и получается простой принцип корневого файла: исполняется только перенос
цели и небольшая вспомогательная логика (списки, формат, сводное покрытие).

### 10. Как `sanitize`/`coverage` передают флаги без `ifeq`

В `01/Makefile`:

```make
sanitize:
	@ASAN_OPTIONS=detect_leaks=1 UBSAN_OPTIONS=print_stacktrace=1 \
		$(MAKE) --no-print-directory BUILD_DIR=$(ASAN_BUILD_DIR) \
		CXXFLAGS="$(CXXFLAGS) -fsanitize=address,undefined -fno-omit-frame-pointer" \
		LDFLAGS="-fsanitize=address,undefined" test
```

Разбор по кускам:

- `ASAN_OPTIONS=... UBSAN_OPTIONS=...` перед `$(MAKE)` — временные переменные
  окружения для этого запуска: `make` их унаследует и передаст тестовому
  бинарнику (детектор утечек и стектрейсы UBSan);
- `BUILD_DIR=$(ASAN_BUILD_DIR)` и `CXXFLAGS=...` в **командной строке** вложенного
  `make` — переопределяют значения переменных внутри вложенного запуска (выше
  мы про приоритет командной строки);
- `test` — цель, которую мы просто «переиспользуем» в другом каталоге и с
  другими флагами;
- флаги записаны явной строкой, без скрытых условностей — так видно, что именно
  компилируется под чем.

Для `coverage` то же самое, но `--coverage -O0` в `CXXFLAGS`, `--coverage` в
`LDFLAGS`, а потом запуск `gcovr`, который из `.gcno/.gcda` в `build-cov/` строит
отчеты. Почему нельзя просто «скомпилировать и запустить одним вызовом без
промежуточных `.o`»: флаг `--coverage` кладет данные профилирования рядом с
объектными файлами, поэтому объекты должны лежать в известном `build-cov/NN/`
— и `gcovr` знает, где их искать.

### 11. Корневой Makefile: разбор оставшегося

```make
HWS := 01          # список работ; новую работу дописывают сюда
HW ?=              # если вызвали make build HW=02 — берется 02
```

Блок выбора каталогов:

```make
ifeq ($(HW),)
  DIRS := $(HWS)          # HW пуст → все работы
else
  DIRS := $(HW)           # HW=02 → только она
endif
```

`FORMAT_SOURCES` — список C++-файлов для `clang-format`, собранный шеллом
(`find` + `sort`): исключаются `.git`, каталоги `build*`, `coverage`,
`third_party`.

В `coverage` корня снова `$(if ...)`:

```make
$(if $(HW),--filter '$(HW)/.*',)
```

если выбрана конкретная работа — `gcovr` ограничивает сводный отчет только ею.

### 12. Полезные команды для отладки

```bash
make -n target         # сухой прогон: показать команды, но не выполнять
make -n lint           # увидеть, что сделает линт, ничего не запуская
make -C 01 test        # выполнить цель прямо в работе (без корня)
make --trace           # подробно: почему пересобирается та или иная цель
```

Типичные грабли:

- **«missing separator»** — осталось строка без таба в начале команды (пробелы
  вместо таба);
- **«Nothing to be done»**, хотя код поменяли — целевой файл не зависит от
  исходника (или забыли прописать зависимость/`.d`);
- `$(VAR)` в рецепте, если хотели шелл-переменную — пишите `$$VAR`.
